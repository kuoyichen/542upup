# 「鎮妹！給問嗎？」活動網頁設計

日期：2026-11-06
雛形（假資料、可點）：https://claude.ai/artifact/Udxf66upqjYDHZ7fw7KqGM
程式所在：本 repo（政策島 Zeabur 自架版），只在 `zeabur` 分支開發，**不推 main**。

## 1. 為什麼做

草屯鎮長政見發表會後有一場「鎮妹！給問嗎？」活動：先蒐集鎮民的問題，活動現場隨機抽題，媛婷當場回答。

- 鎮民在活動網頁提問，問題自動出現在網頁列表，也變成政策島上的留言瓶。
- 鎮民在網頁上看得到所有問題，可以按「我也想問」。
- 團隊在後台可以把問題從列表隱藏，或排除在抽選庫外。
- 活動當天，團隊用接投影的筆電抽題，投影顯示題目，媛婷照題回答。

時程：使用者要求「越快越好」上線收題。活動日期未定（見第 11 節）。

## 3. 目標、非目標、反目標

**目標**
- 收題頁上線越快越好；抽題頁在活動前完成。
- 現場抽題穩定：主持人按下去一定有題目出來，投影上絕不出現已隱藏的內容。
- 鎮民不用登入，三步內送出問題。

**非目標**
- 不做登入或會員，不收電話、LINE 等聯絡方式。
- 不做議題分類、不做先審後公開。
- 不做手機遙控投影。
- 不改原作者的 main 分支與 Vercel 版本。

**反目標（做出來但等於失敗）**
- 投影或列表出現已隱藏的題目。
- 活動當下網路一抖，抽題頁卡住或抽不出來。
- 開發或測試時把資料寫進正式 Upstash。
- 島上原有的留言瓶、媛婷回覆、瀏覽數因這次改動壞掉。

## 4. 現況（動工前要知道的）

- 站是單一 `index.html` 加 `api/*.js`，由零依賴的 `server.js` 轉接（Zeabur 服務 `island`，Node 24，PORT 8080）。`server.js` 用 `ROUTES`（api）和 `PAGES`（無副檔名頁面）兩張表分流，目前不看 Host。
- 留言瓶：`api/bottles.js`，Upstash list `542upup:bottles`，每則 `{id,t,text,name}`，只保留最新 200 則，島上顯示最新 30 則。過濾：去控制字元與 `<>`，擋網址與常見髒話；每位訪客（`vid`）45 秒一則，全站每小時 120 則。
- 媛婷回覆：hash `542upup:replies`（瓶子 id → `{text,t,by}`），`api/replies.js` 公開唯讀只回保留中瓶子的回覆，不給 `by`。寫入走 `api/admin.js`（需登入）。島上打開瓶子時顯示「媛婷回覆」區塊（純文字）。
- 後台帳號：`/reply` 的個人帳號（`smalt` 小編、`nantou_yt` 媛婷），session 在 `reply:sess:*`，邏輯在 `api/admin.js`。
- 資料庫跟原作者的 Vercel 版共用同一份 Upstash。Vercel 版的留言瓶 API 是原作者的程式，從那邊丟的瓶子也會進 `542upup:bottles`。
- 測試：`npm test`（node --test）；`dev/fake-upstash.js` 是記憶體假 Upstash，UI 檢查一律接假 Upstash。

## 5. 畫面

照雛形，三個畫面都在 `ask.542upup.tw`：

1. **鎮民頁** `/`：標題「鎮妹！給問嗎？」、提問表單（暱稱、里別下拉、問題 120 字含字數）、送出鈕「丟進留言瓶」；下方列表可切「最多人想問／最新／已回答」，每題有「我也想問」計數鈕；已回答的題目顯示「活動中已回答」與影片連結（還沒貼影片就寫「回答影片整理中」）。收題關閉時表單換成「已截止」說明，列表照常顯示，「我也想問」照常可按。
2. **投影抽題** `/draw`：16:9 深色舞台（固定一套顏色，不跟系統深淺色切換），角落放現場提問 QR code；空白鍵抽題、拉霸滾動停在一題，顯示題目、暱稱·里別、幾人也想問、線上或現場；下方操作列在全螢幕時隱藏，全部可用鍵盤操作（見第 7 節）。
3. **後台** `/admin`：線上提問、現場提問兩個開關；統計（總數、公開、兩個抽選庫、已回答、已隱藏）；篩選（全部／線上／現場／政策島留言／已隱藏／已排除／已回答）；每題可隱藏、排除抽選、改線上或現場、勾已回答並貼影片連結；顯示每題「我也想問」數與在所屬池子裡的抽中機率。

里別清單只有草屯鎮正式里名（27 里，來源：中選會 111 年草屯鎮里長選舉公報），不加「外地鄉親」（使用者 11-06 決定）；里別必選。上線前請使用者核對里名。

## 6. 資料模型與流程

所有 key 沿用 `_redis.js` 的前綴 `P`（`542upup:`）。

**提問清單**（新）：每題一筆，至少包含 `id`、`t`、`text`、`name`、`vil`（島上來的為空）、`origin`（`ask` 或 `island`）、`src`（`online` 或 `live`），以及能從 `542upup:bottles` 精準移除那則瓶子所需的資料（LREM 需要原字串）。狀態欄位：`hidden`、`excluded`、`answered`、`drawn`、`video`。

**我也想問**（新）：每題計數，加上每題已按過的 `vid` 集合；同一 `vid` 對同一題只算一次，可以取消。票數的單一事實來源是投票者集合的大小（`SCARD ask:voters:<id>`）（11-06 審查後改：舊的 `ask:votes` hash 不再讀寫，留在資料庫無害）；加減與讀回合成同一個 pipeline（`SADD|SREM` + `SCARD`）。另有 `ask:vc`（hash，id → 票數）當 SCARD 的快取：`ask-vote` 在上述 pipeline 之後多一趟 `HSET ask:vc <id> <SCARD 結果>`（寫失敗吞掉，投票者仍拿到精確票數）；`readAll` 平常只在第一個 pipeline 加一條 `HGETALL ask:vc` 取票數（缺值視為 0），不再逐題 SCARD，避免 Upstash 依指令數計費時列表輪詢（公開頁 5 秒、後台 20 秒、投影 15 秒）爆量。快取自癒：每個 process 至多每 10 分鐘（含啟動後第一次讀取）對帳一次，逐題 SCARD（每個 pipeline 至多 500 條），該次讀取採用 SCARD 結果，並只把與快取不同的題目 `HSET` 寫回；兩個並行投票的 HSET 亂序（後寫者帶舊值）造成的偏差，最多維持到該題下一次有人投票或下一次對帳。

**收題開關**（新）：線上、現場各一個布林值；線上另記最近一次關閉的時間（流程 2 要用）。

要求：多個後台同時操作、鎮民同時按「我也想問」時，狀態與計數不能互相覆蓋（不要把整筆 JSON 讀出改完再整筆寫回）。實際 key 怎麼切交給實作者。

**流程**

1. **活動頁提問**：驗證同留言瓶（相同過濾、120／16 字），檢查對應的收題開關。寫入提問清單，同時 LPUSH 一則瓶子進 `542upup:bottles`（多帶 `vil` 和標記欄位，例如 `ask:1`，原欄位不變），照舊 LTRIM 到 200。
2. **島上留言進提問列表**：讀 `542upup:bottles`（LRANGE 0 199），清單裡還沒有的瓶子補建一筆（`origin: island`、`src: online`、預設進抽選庫）。這樣 Zeabur 版和 Vercel 版丟的瓶子都收得到，也順便完成「舊留言匯入」。補建在讀列表時順手做（公開列表與後台列表），不需要另外排程。已經存在的不覆蓋，所以被隱藏的不會因同步又冒出來。線上收題關閉期間，瓶子時間 `t` 晚於關閉時間的，補建時預設 `excluded`（使用者決定：進列表、不進抽選庫）；重新開放後新來的恢復預設進抽選庫。島上丟瓶子本身不受開關影響（Vercel 版也擋不了）。
   **在別處被刪的瓶子（使用者 11-06 決定自動偵測）**：題目的瓶子不在清單裡，而且它比清單裡最舊那瓶還新超過 60 秒（那就不可能是被自然擠出；寬限是因為各寫入端的時鐘與網路來回，讓 t 不一定照進清單的順序）時，視為在 Upstash 後台或原作者那邊被刪，自動隱藏並排除抽選，後台標「瓶子已在別處被刪除」，可用「恢復公開」救回；比清單最舊還舊的缺席題目分不出是擠出還是被刪，一律不動（已知缺口：刪掉最舊的幾瓶偵測不到，可在後台手動隱藏；11-06 審查後改，不再記「清單滿過」，因為島上寫入端不會留下紀錄）（沒被隱藏的題目按恢復公開不做任何事）。刪不當瓶子請一律走活動後台「隱藏」。

   **每題後台鎖（11-07 第三輪審查）**：改動單一題目的後台操作（hide／unhide／exclude／include／src／answer／video／draw／putback）在驗證輸入後、讀取前先 `SET ask:lock:<id> <隨機token> NX EX 10`，持有到讀取、資格檢查、寫入、快取失效、抽選的認領與驗證、回覆同步全部做完才放，放鎖用 `finally`，且只在鎖值仍是自己的 token 時才 `DEL`（鎖過期被別人重拿就不動）。拿不到鎖：抽選回 409 `unavailable`（投影頁照舊換一題），其他操作回 409 `busy`（後台頁顯示「另一位同事正在改這題，請稍後再試」並重抓列表）。這取代原本只有恢復公開才有的鎖，一併擋掉「隱藏卡在恢復公開的 LPUSH 與 SREM 之間」與「影片同步晚於取消回答」兩種並行交錯。`open` 開關不針對單一題目，不取鎖。
3. **隱藏**：標 `hidden`，同時標 `excluded`（使用者決定：隱藏就直接排除）；取消隱藏不清 `excluded`，要團隊另外放回抽選。從 `542upup:bottles` LREM 那則瓶子（已被 LTRIM 擠掉就略過）。公開 API、投影抽選庫都不回 hidden 的題目。**取消隱藏**：重新 LPUSH 原字串（會變成島上最新的一瓶，可接受，我的決定）。瓶子 id 不變，回覆對應不會斷；LPUSH 前先確認清單裡沒有同一則，避免重複。隱藏期間「我也想問」票數與已按過的 `vid` 都保留（我的決定）。
4. **排除抽選**：只標 `excluded`，列表照常。
5. **已回答＋影片**：標 `answered`、存 `video`。有影片時寫一則回覆到 `542upup:replies`（瓶子 id 同題目對應的瓶子），島上「媛婷回覆」區塊顯示說明文字與影片連結。`replies` 現在只有 `text`，要加可選的影片網址欄位，`api/replies.js` 一併回傳，島上渲染成可點的連結。（更正 11-06：/reply 原本會刪掉不在清單裡的瓶子的回覆；現在提問列表裡有的題目一律不算孤兒，回覆保留。）島上的瓶子已被擠出保留範圍時，島上看不到回覆，但回覆不會被刪。
   回覆文字規則（我的決定）：那則瓶子還沒有回覆時，寫入固定文字「這題在「鎮妹！給問嗎？」活動中回答了，點下面看影片。」加影片網址，`by` 記操作的後台帳號；已經有人用 /reply 寫過回覆時，保留原本的文字與 `by`，只補影片網址。取消「已回答」或清掉影片時，只拿掉影片網址；若文字是上面那段固定文字，整則回覆刪除。`api/replies.js` 會丟掉沒有 `text` 的回覆，所以影片網址一定要配非空文字。

## 7. 抽題規則

- 兩個池子：**線上池**＝`src: online`（活動頁線上提問＋島上留言）；**現場池**＝`src: live`（現場掃 QR 提問）。
- 抽選庫＝未隱藏、未排除、未回答、未在本輪被抽出的題目。後台抽出（draw）先 `SADD ask:drawn` 認領，再一趟 pipeline 驗證仍未隱藏、未排除、未回答且題目存在；任一不符就 `SREM` 回去並回 409（11-06 審查後補，防止 readAll 快照之後才被隱藏的題目仍被抽出）。
- 權重＝1 + √(我也想問數)（**我的決定**，避免一題獨大：0 票權重 1、4 票 3、25 票 6、100 票 11）。後台顯示的抽中機率用同一個公式。
- 輪流：每題結束自動換邊，線上 → 現場 → 線上。現場那輪若現場池是空的，自動切「現場舉手」。主持人可隨時按 1／2／3 指定線上題／現場 QR 題／現場舉手。
- 現場舉手：不抽系統裡的題，投影顯示「現場舉手提問」畫面，按 Enter 結束這輪。
- 抽到後：Enter＝回答完、標已回答、下一題；R＝不算，放回抽選庫；X＝排除這題。F＝全螢幕。
- 拉霸先決定結果再播動畫；`prefers-reduced-motion` 時縮短動畫。

**現場網路不穩的要求**：投影頁要登入（它會改狀態）。開頁時抓一次抽選庫快照，之後在待機時定期更新（讓現場剛送的 QR 題進來）；抽題在頁面本地算，不必等網路。標記結果（抽出、已回答、放回、排除）寫回失敗時排隊重試，不擋下一次抽題。頁面要能從斷線恢復，不能因一次請求失敗卡住。

**快照與「絕不顯示已隱藏」的取捨（我的決定）**：拉霸動畫一開始就向伺服器確認抽中的題目還在抽選庫（逾時約 1.5 秒，動畫本身約 3.6 秒，通常感覺不到）。確認回來已隱藏或已排除，就在動畫結束前換成重抽的結果；逾時或斷線才直接用快照結果顯示，並只在操作列（不在投影上）標「離線抽題，未確認」，主持人覺得不對可以按 X。殘餘風險是「快照更新後才隱藏、又剛好斷線」，機率很低，主持人把關。

**抽出未處理（我的決定）**：`drawn` 存在資料庫，直到主持人按 Enter、R 或 X。關頁或重整後再開投影頁，先顯示「上次抽出、還沒處理」的那題讓主持人處理。後台也可以把「剛抽出」的題目放回抽選庫。不會跨天自動清除。離線時排隊的標記，恢復後依操作順序送出，伺服器端以最後一個操作為準。

## 8. 現場 QR code

QR code 指向帶現場標記的網址（例如 `ask.542upup.tw/?live=1`），從這裡送出的題目 `src: live`，頁面顯示「你在活動現場，這題會放進現場題」。標記可被轉傳濫用，後台可以手動改線上或現場（**我的決定**，接受這個風險）。現場提問受「現場收題」開關控制，線上提問受「線上收題」開關控制。

## 9. 政策島要改的地方（只改 zeabur 分支）

- 有活動標記的瓶子：島上瓶子本體或打開後的紙條貼「鎮妹給問」標籤，並附活動頁連結。
- 「媛婷回覆」區塊支援影片連結。
- 其餘行為（顯示最新 30 瓶、丟瓶子流程）不變。提問一多會把一般訪客的瓶子擠出畫面，使用者選擇雙向同步即接受這點。
- Vercel 版看得到活動頁來的瓶子（沒有標籤、沒有影片連結），隱藏後兩邊一起消失。

## 12. 測試與安全邊界

- 測試與本機開發一律不碰正式 Upstash：`npm test` 用 mock；UI 檢查用 `dev/fake-upstash.js`（需補上新用到的 Redis 指令）；本機起 server 時清空 `KV_REST_API_URL`／`KV_REST_API_TOKEN` 或指向假 Upstash。
- 既有測試（約 59 個）要全過，並為新 API 補測試：輸入驗證、收題開關、hidden 不外流（公開列表、投影快照）、「我也想問」同一 vid 只算一次、同步不覆蓋既有狀態、隱藏時 LREM 正確那則。
- 不收個資：表單提示「不要寫電話、地址」。暱稱、里別、問題全公開。
- 內容過濾沿用留言瓶規則；先公開後審，收題期間團隊要有人看後台。
- 提問速率上限（11-06 審查後補）：每台裝置 45 秒一題（被擋的請求不計入其他上限）、每個 IP 每小時 100 題（IP 以 cf-connecting-ip 為準，不信任用戶端自填的 X-Forwarded-For）、全站每小時 600 題。「我也想問」每 IP 每小時 400 次，同樣以 cf-connecting-ip 為準；投票不清公開列表快取（最多 5 秒後其他人才看到新票數）。
- 來源鎖（防繞過 Cloudflare 直連源站、偽造 cf-connecting-ip）：server.js 要求每個請求帶 `x-origin-key`，值須等於環境變數 `ORIGIN_SECRET`（timingSafeEqual 比對），否則回 403 `forbidden`；標頭由 Cloudflare 的 Request Header Transform Rule 為 ask.542upup.tw 與 island.542upup.tw 兩個主機名加上。`ORIGIN_SECRET` 未設定＝不檢查。上線順序：先部署程式碼，再在 Cloudflare 加規則，最後才在 Zeabur 設環境變數；回滾＝刪除該環境變數。
- 留言瓶每個 IP 每小時最多 30 則（`bottle:ip:<ip>:<小時>`，排在每台裝置 45 秒之後、全站每小時之前；被擋的請求不動全站計數），換 vid 也繞不過。
- 後台登入／改密碼的失敗限制改為「先預扣再驗」：驗 scrypt 前先原子 INCR 該 IP（8 次／15 分鐘）與全站小時（60 次）計數，該 IP 的計數 key 依整點對齊的 15 分鐘窗口命名（`reply:fail:<ip>:<窗口編號>`，TTL 30 分鐘），key 名不跨窗口重用，遲到的還款只動自己的窗口，鎖定最長 15 分鐘；超過就 429 並把這次預扣還回（被擋的請求不佔額度）；密碼正確只還回自己的預扣、不清空該 IP 的計數（先前的失敗留在窗口內到期歸零，避免並行還款讓計數變負）。
- 對 Upstash 的每個請求（含讀 body）有逾時，預設 8 秒（環境變數 `REDIS_TIMEOUT_MS`）；逾時丟錯，呼叫端回 502，公開列表共用的讀取也會被清掉，不會卡住所有人。
- 公開列表快取：同時進來的讀取共用同一次資料庫讀取；後台隱藏後，進行中的舊讀取不會把已隱藏的題目寫回快取。
- 後台「隱藏」要按兩次確認。

- 共用原作者的 Upstash：寫入格式只能「加欄位」，不能改既有欄位，避免 Vercel 版壞掉。
